# 공모전 아이디어 검토

## 문서 정보

- 상태: 조사 기록. 현재 출품 주제는 [출품 주제 선정](1005_출품_주제_선정.md)을 따른다. 아래 판정은 주제 선정 전 조사 결과이며 기술 검증 완료를 뜻하지 않는다.
- 적용 범위: 출품 아이디어 조사와 탈락 근거. 제품 기능·개발 범위의 확정 문서가 아니다.
- 근거: 2026-10-28 사용자의 루프 엔지니어링 조사 목표와 아래 확인한 원문. 확인일은 2026-10-28이다.
- 관련 요구사항: REQ-CONTEST-001, REQ-CONTEST-009. 대회에서 정한 조건과 사용자의 추가 신규성 기준은 구분한다.
- 실행 방식: 코디네이터 1명, 발굴 워커 2명, 독립 검증 워커 1명. 발굴·검증 결과를 통합하되 워커 요약만으로 신규성을 확정하지 않는다.

## 목적과 범위

기존 기능의 재포장과 검증되지 않은 후보를 반복 추천하지 않도록 문제 근거·경쟁 사례·데이터·탈락 이유를 유지한다. 목표는 서로 겹치지 않고 신선하며 실제 구현 가능한 신규 기능 3개와 최종 비교·추천이다. 목표는 아직 미달성이다.

### 사용자 조건

- Pleos Connect 앞좌석 중앙 화면에서 실행되는 별도 Android 앱이다. 기존 UI·운영체제를 대체하지 않는다.
- 내연기관·하이브리드·전기차 공통 문제를 우선한다. 휴대폰·QR·별도 센서·하드웨어 필수 구성은 후순위다.
- 앱을 여는 시점, 해결할 일, 종료 시점을 설명한다. 운전 중 복잡한 조작·지속 주시를 요구하지 않는다.
- 내비 오버레이·자동 화면 전환·백그라운드 실행을 임의로 전제하지 않는다.
- 실문제 근거, 별도 앱의 가치, 중앙 화면·차량 데이터의 핵심 역할, 스마트폰 대비 추가 가치가 필요하다.
- AI 추가·큰 화면·기능 통합·국내 미출시·희귀 사용자만으로 차별성을 주장하지 않는다.
- 공모전 시연 범위와 외부 데이터·제휴의 비용·조건·불확실성을 밝힌다.
- 한국·해외 제품, 제조사 기본 기능, 앱스토어, 연구·시제품을 대조한다. 판매·시범·출시예정·연구 상태를 구분한다.
- 공식 자료와 원문을 우선한다. 검색 무결과를 부재 증거로 삼지 않는다.
- API 선언·승인·에뮬레이터·실차를 구분한다. 정보의 정확도·주기·누락·권한 거부·연결 끊김을 검토한다.
- 데이터 경로는 Pleos SDK / Android 일반 API / 외부 API / 사용자 입력 / 직접 구축 / 기기·제휴로 분류한다.
- 실내 온도를 물품 온도로, 정차를 신호 대기로, 벨트 상태를 신원으로 해석하지 않는다.
- 후보의 위험한 가정과 최소 확인 방법·탈락 조건을 정의한다. 실행하지 않은 기능은 정상 작동으로 쓰지 않는다.
- 완성 산출물에는 후보별 비교 표, 최종 추천과 시나리오, 경쟁 기능 대조, 사실·가설·미확인 구분, 탈락 근거와 출처가 필요하다. 개수를 채우려고 기준을 낮추지 않는다.

### 재제안하지 않을 기존 영역

충전소·휴게소·여행지·주차장 추천; 왕복 배터리·충전 시간·미래 이동 에너지 예산; 가족·반려동물 휴식; 교대·합류·투표; 여행 기록·타임캡슐·위치 이야기; 차량 게임; 설명서·설정 추천·작동 조건; 인수인계·반납·짐 배치; 시승·전비·불편 기록; 동승자 소통·번역·자막·요청·익명 질문·정산; 임시 계정·삭제·개인/공유 화면; 공조 체감·음향 평가·자동화·실행 확인; 접근 가능한 하차·충전 자리; 그림 일정 기반 동승자 안내. 명칭이나 사용자만 바꾼 변형도 제외한다.

## 검증 기준과 현재 판정

| 검증 항목 | 통과에 필요한 근거 | 현재 상태 |
| --- | --- | --- |
| 직전 답변 감사 | 기존 원리·사용자 제외 범위와 중복되지 않음 | '여유길' 탈락: 아래 원논문과 핵심 원리 동일 |
| 실제 문제 | 사용자 과업과 불편이 원문으로 확인됨 | 후보별 확인 필요 |
| 차별성 | 가장 가까운 제품·연구와 핵심 사용자 과업 비교 | 현재 신규 통과 0개 |
| 기술 | 필요한 데이터·권한·실행 환경을 구체화 | 정책 조사 완료 항목과 실행 미확인 분리 |
| 구현 가능성 | 핵심 불확실성의 확인 방법과 제한된 시연 범위 | 최종 후보가 없어 미완료 |
| 최종 산출물 | 중복 없는 신규 기능 3개 및 사용자 지정 표·추천·시나리오 | 미완료 |

동일 핵심 원리가 선행 연구에 있으면 제품 포장 차이만으로 '존재하지 않았던 기능'으로 계산하지 않는다. 반대로 같은 센서·기술을 사용했다는 사실만으로 모든 새 사용자 과업을 탈락시키지도 않는다. 최종 판단은 사용자 과업과 핵심 동작을 비교한다.

세계 모든 제품·비공개 개발물·특허에 존재한 적 없다는 절대 명제는 공개 웹 검색만으로 입증할 수 없다. 이 한계를 이유로 목표를 달성했다고 바꾸어 쓰거나 검색 무결과를 통과로 기록하지 않는다.

추가 검토에서 완전한 동일 기능 여부를 확인하지 못한 '운행 기반 자동차 비소유 대안 검토', '예약 취소·대체권 계약'도 통과 후보가 아니다. 전자는 차량 화면의 필요성이 약하고, 후자는 실제 예약권·취소권 API 또는 사업자 제휴가 필요하며 기존 일정·예약의 재포장 위험이 남는다.

## 추가 발굴과 사후 분실물 탐색 가설

새 사용자 과업을 먼저 설계한 추가 발굴에서도 출발 시각 변경 보상, 이동 중 물품 운송, 차량 유휴 연산 공유 등은 선행 서비스·연구가 확인됐거나 플랫폼 자원 접근 조건이 미확인이었다. 차량 공간 임대는 일반 시간제 공간 임대 대비 추가 가치와 차량 접근·운영 조건을 확보하지 못해 추천하지 않는다.

### 후보 LOST-01: 태그 없는 분실물의 역방향 탐색

**현재 판정은 보류·최종 통과에서 제외다.** 같은 문제를 다루는 선행 문헌이 확인됐고, 구체적인 도어 조건 필터 차이만으로 사용자가 요구한 신규 기능 3개에 포함할 근거는 아직 부족하다.

| 항목 | 가설과 근거 |
| --- | --- |
| 사용자·문제 | 차로 여러 장소를 방문한 뒤 없어진 안경·지갑·서류 등을 어디부터 다시 확인할지 결정. [Uber 공식 분실물 자료](https://www.uber.com/us/en/newsroom/the-2026-uber-lost-found-index/?nocache=true)는 차량 내 분실의 존재를 뒷받침하지만 자가용 사용자 수요·제품 효과를 증명하지 않음 |
| 시작·종료 | 정차 중 물건 찾기 → 마지막 확인 시점·관련 문(선택) 입력 → 확인 목록 선택 → 찾음 또는 탐색 종료 |
| 제안 기능 | 수집이 실제로 유지된 구간의 문 열림·시각·위치를 기억 조건과 대조. 물건 자체를 감지하거나 특정 장소에서 잃었다고 판단하지 않음 |
| 차량 추가 가치 | 스마트폰 GPS에 없는 도어 접근 이벤트. 휴대폰을 잃은 경우에도 차량에서 실행할 수 있다는 가설. 차키 분실처럼 차량에 접근하지 못하는 상황은 대상에서 제외 |
| 데이터 경로 | Pleos 도어 capability·리스너, NaviHelper 또는 승인된 위치 API, Android 수신 시각·로컬 DB, 사용자 기억 입력 |
| 첫 시연 범위 | 명시적인 모의 이벤트·좌표로 검색 UI 확인. 별도 실제 SDK 단계에서 foreground 도어 이벤트·위치 수집을 확인해야 함. 현재 둘 다 미실행 |
| 기술 탈락 조건 | 앱 전환·프로세스 종료·차량 전원 변화 중 누락이 커서 탐색을 돕지 못함. 위치 품질을 구분할 수 없음 |
| 신규성 탈락 조건 | 같은 도어 조건 기반 사후 탐색 기능의 직접 선행 사례 확인 또는 기존 분실 위치 추정 기능에 센서 변경·조건 필터만 더한 수준으로 판단됨 |

### 데이터와 수명주기 확인 조건

- `DoorPositionListener.onPositionUpdated(pos: Int?)`의 기록에서는 발생 시각·도어 ID를 직접 받는다고 확인하지 못했다. 등록 영역으로 도어를 연결하고 앱 수신 시각을 차량 원본 발생 시각과 구분해야 한다. 문 위치 범위도 차량별 capability를 확인한다.
- 현재 위치 수신 시각이 최근이라는 사실만으로 위치 원본 측정 시각·정확도가 보장되지 않는다. 품질을 모르면 지점 확정을 보류한다.
- 과거 도어 이력 조회 API는 확인되지 않았다. 기록 시작 전 이력을 복원할 수 있다고 가정하지 않는다.
- [공식 앱 동작 모델](https://document.pleos.ai/docs/pleos-only/vehicle-app-planning-guide/app-structure-screen-model)은 배경에 남을 수 있음을 설명하지만 상시 수집·자동 부팅·차량 전원 종료 중 수집을 보장하지 않는다.
- 문 열림은 물건 이동의 증거가 아니며, 미개방도 분실 없음의 증거가 아니다. 관련 문 기록을 먼저 묶더라도 나머지 기록·차내 잔류·기억 오류·누락 구간을 숨기지 않는다.
- 확인 순서는 최근순·오래된 순 등 사용자 선택으로 표시한다. 근거 없는 분실 확률·자동 순위를 만들지 않는다.
- 실제 기능 검증 전에는 모의 UI와 foreground 이벤트 수신만으로 실사용 가능 판정을 내리지 않는다.

### 이동 중 디지털 작업 완결 가설

대용량 자료 준비, 원격 빌드, 문서 위임, 회의 대행, 사전 승인 거래, 개인 업무 대행, 기기 간 인계, 현장 문서 조립, 위치 기반 자원 반환, 계산 작업 분할·이관의 10개 가설을 검토했다. 대부분 이동·정차를 기존 기능의 실행 트리거로 쓰는 수준이어서 추천하지 않았다.

가장 구체화한 가설은 예상 이동경로·연결 가능 시간·도착 마감을 이용해 계산 작업을 이관하여 결과물을 완성하는 앱이었다. 그러나 [TU Berlin 연구진의 2025년 원문](https://www.tkn.tu-berlin.de/bib/zhou2025task/zhou2025task.pdf)은 차량 체류시간 예측과 마감시간을 고려한 작업 이관을 이미 제안한다. 코디네이터는 출판사 검색 추출 초록 및 연구진 공개본의 추출문을 대조했으며, 출판사 직접 열기는 403으로 실패했다. 연구 시뮬레이션이며 출시 차량 앱으로 확인한 것은 아니다.

사용자용 작업 선택 화면을 붙이는 차이만으로는 이 후보의 핵심 차별성을 설득하기 부족하다. 외부 계산 인프라·통신 예측·백그라운드 실행·열 제한도 확보되지 않았다. 후보를 통과시키지 않으며 실제 Pleos 동작을 검증한 것으로 표시하지 않는다.

### 식품 노출 이후 처리 순서 결정 가설

차량 내 식품의 온도 노출을 보고 귀가 후 냉장·조리·확인 순서를 정하는 과업을 검토했으나 통과시키지 않았다. [Toyota 공개 특허 US20220024280A1](https://patents.google.com/patent/US20220024280A1/en)의 청구항 1은 차량 센서와 화면으로 부패 가능 물품의 보관 가능 시간을 추정하고 상태를 갱신하는 구조, 청구항 2는 부패 가능성 순서의 품목 표시를 명시한다. 코디네이터가 청구항 원문을 직접 대조했다. 출시 제품 여부나 법적 권리 범위는 판단하지 않았다.

앱이 경고를 넘어 처리 순서를 제시한다는 차이도 선행과 겹친다. 더구나 실내 공기 온도는 포장·보냉재·초기 온도·위치가 다른 식품의 온도를 증명하지 못하므로 섭취·폐기 판단의 입력으로 대체할 수 없다. 새 온도센서·품목별 검증모델 없이 안전한 처분 결정을 보장한다는 기획은 제외한다.

### 개발자 도구·신호 이용 검토

실제 앱의 API 실패 조건을 유지하며 콜백 시퀀스를 줄여 재현 테스트를 생성하는 개발자 도구를 조사했다. [RemotiveLabs 공식 제품](https://www.remotivelabs.com/applications/android-automotive)은 이미 실차·기록 신호를 AAOS/VHAL·위치·센서에 공급하고 재생하여 버그를 재현한다. 코디네이터는 제품 원문을 확인했다. 최소 입력 생성은 추가 설계 여지가 있지만 기록·재생 기능 자체를 신규로 설명하지 않는다.

독립 앱이 다른 앱의 내부 실패 조건과 콜백을 읽을 수 있다는 근거는 없다. 대상 앱에 관측용 SDK를 넣는 협력이 필요하며, 이 경우 별도 차량 앱보다 개발용 라이브러리·분석 도구가 중심이 된다. 전체 차종 지원표도 앱별 접근 권한과 미지원의 구분 없이는 확정할 수 없다. 현재 차별성과 독립 앱 필요성이 부족하여 최종 후보에 넣지 않는다.

목적별 신호 이용 동의·최소 신호 레시피도 검토했으나 다른 앱의 직접 SDK 접근을 제한하는 플랫폼 권한을 확보하지 못했다. 협력 앱이 따르는 설정을 만드는 것과 시스템 차원의 최소 신호 사용 보장은 다르다. 개인정보 통제의 변형으로 추천하지 않는다.

기획 조사 중 `adb devices -l`에서 Pleos `crp_avd` 에뮬레이터 연결, 패키지 목록에서 Vehicle·Navi·위치 서비스 설치를 새로 확인했다. 과거의 연결 기기 없음은 현재 차단 사유가 아니다. 하지만 이 확인은 SDK 호출·권한·capability 검증이 아니며, 후보의 기술 통과 근거로 대체하지 않는다.

### 재검증 후보 API-DIAG-01: 차량 API 원인 분리 실험기

현재는 최종 통과가 아닌 검증 대상 가설이다. 앞선 기록·재생 도구와 달리, 이미 있는 로그를 보여주는 대신 서로 구별되지 않는 원인들을 나누기 위한 다음 현장 실험을 선택한다. 단순히 대상 사용자를 개발자로 바꾸는 것만으로 신규성을 주장하지 않는다.

| --- | --- |
| 사용자·문제 | 차량 앱 개발자가 값 없음·고정값·콜백 누락을 만났지만 미지원·권한·공급자 상태·앱 내부 전달 문제를 구분하지 못함. 차량별 문제 빈도와 절감 효과는 미측정 |

| 차량 필요성 | 해당 차량의 실제 공급 데이터·접근 권한·구독 경로를 관찰해야 함. 서버 로그나 다른 차량의 시뮬레이션만으로 이 조건을 확정할 수 없음 |

| 기술 제약 | 다른 앱 내부를 임의 관찰할 수 없음. 권한은 앱이 대신 부여하지 못함. SDK 호출로 분리할 수 없는 미지원/권한 문제는 미확정 유지. 차량 제어·주행이 필요한 실험은 자동 실행하지 않음 |
| 탈락 조건 | 고정 체크리스트보다 필요한 관찰 수·개발자 판단 부담이 줄지 않음, 대상 앱 협력 없이는 핵심 동작이 성립하지 않는데 협력 경로를 확보하지 못함, 공개 선행이 같은 앱 컨텍스트의 적응형 실험 선택을 이미 제공하거나 공모전 출품 범위에 맞지 않음 |

가까운 선행은 [RemotiveLabs](https://www.remotivelabs.com/applications/android-automotive)의 신호 기록·재생과 [ISSTA 2022 PermDroid](https://conf.researchr.org/details/issta-2022/issta-2022-technical-papers/31/PermDroid-Automatically-Testing-Permission-Related-Behaviour-of-Android-Applications)의 관련 권한 조합 탐색이다. 코디네이터는 제품 설명과 학회 원문 초록을 확인했다. 전자는 재현 입력 공급, 후자는 권한 관련 동작 탐색을 설명한다. 이 설명만으로 적응형 현장 원인 분리 기능이 없다고 단정하지 않는다. 능동 진단·실험 선택 알고리즘 자체는 새 기술로 주장하지 않는다. 추가 제품·논문·특허 대조와 공모전 적합성 확인이 남아 있다.

독립 검토에서는 최종 통과 대신 검증 대상으로 유지할 가치가 있다고 판단했다. 대상 앱 UID의 증거를 얻으려면 probe가 대상 앱 프로세스 안에서 실행돼야 한다. 직접 조회와 콜백은 시간차·캐시·연결 세대가 달라 같은 값을 보장하지 않으므로, 실험 규칙에 이 차이를 포함해야 한다. 무응답은 원인 확정 증거가 아니며 '최소 실험 횟수'는 정의한 가설·실험 모델 안에서 입증한 경우에만 표현한다. 권한 거부·미지원·연결 단절·구독 수명주기 오류를 넣은 자체 샘플에서 고정 체크리스트 대비 관찰 수와 오판을 비교하는 것이 첫 확인 과제다. 현재 이 실험은 미실행이다.

코디네이터도 [대회 개요](https://appdevchallenge.auto-hmg.io/guide/overview)·[심사 기준](https://appdevchallenge.auto-hmg.io/guide/judging-awards)·[참가 규정](https://appdevchallenge.auto-hmg.io/guide/rules)의 본문을 직접 대조했다. 개요는 운전자·탑승자에게 제공하는 경험을 목적에 두며 심사 기준은 해당 사용자의 문제·해결 방식과 모바일 대비 차량의 독자적 가치를 필수 평가한다. 주제는 예시에 한정하지 않는다. 참가 규정에서 개발자 도구·probe의 명시적 금지를 찾지 못했다는 결과는 취지 적합성이나 접수 승인을 뜻하지 않는다. 따라서 API-DIAG-01은 별도 기술 가설로 보존하되, 운전자·탑승자 가치가 입증되기 전에는 공모전 추천의 우선 후보로 삼지 않는다.

### LOST-01에 추가된 반론

[GO-Finder 연구진 원문](https://www.ut-vision.org/publication/2021-yagi-gofinder/)과 [공개 논문](https://arxiv.org/abs/2101.07314)은 2021년에 이미 물건 사전 등록 없이 웨어러블 영상에서 손으로 다룬 물체를 발견하고 마지막 출현을 조회하는 방식을 제안했다. 따라서 '사전 등록이 없다'는 조건 하나는 LOST-01의 독창성 근거가 아니다. 관측된 차량 접근 기회와 사후 기억 조건을 대조하는 처리 차이가 실제 확인 부담을 줄이는지 확인해야 하며, 분실 장소를 아는 기능으로 표현하지 않는다. 여전히 최종 통과 후보에 포함하지 않는다.

기억의 확실성이 다를 때 질문을 하고 탐색 계획을 갱신하는 재설계도 검토했다. [Alarm.com US11544924B2 원문](https://patents.justia.com/patent/11544924)은 마지막 소지 장소 질문, 복수 사건·위치 가설 그래프, 사용자 확인·부정에 따른 의존 사건·후보 위치 갱신을 설명한다. 사용자 판단 오류를 고려해 가능성을 완전히 없애지 않는 구현도 명시한다. 코디네이터가 해당 설명을 직접 대조했다. 따라서 '기억 수정→가설 갱신→후보 변경' 자체도 신규 근거가 아니다. 확률 없이 대안 기억을 병렬로 보존하고 어떤 추가 확인이 계획을 가장 크게 바꾸는지 선택하는 동작까지 동일한지는 미확인이지만, 현재 차이의 실효성도 입증하지 못했다. 보류를 유지한다. 특허의 권리 침해나 상용 출시 여부는 판단하지 않는다.

### PRIV-01 검토: 공개 전 최소 누출 증거 실험

새 과업으로 자기 차량 신호를 연구 등에 제공하기 전에, 좌표를 제외한 속도·조향만으로 참조 경로가 구별되는지 직접 시험하는 안을 검토했다. 사용자가 필드·시간 구간을 가리고 같은 시험을 반복하여 공개 범위를 결정한다. 더 강한 변형으로는 구별 결과를 유지하는 최소 신호 조각을 찾아 가릴 대상을 제시하는 동작을 가정했다. 실제 외부 공개·업로드는 수행하지 않았다.

| 항목 | 확인 결과와 제약 |
| --- | --- |
| 문제 근거 | [Privacy pitfalls 연구](https://www.sciencedirect.com/science/article/pii/S2214209622001127)는 속도·조향 신호로 궤적을 재구성할 수 있음을 연구했다. 해당 실험의 성능을 Pleos·모든 운전자에 일반화하지 않음 |

| 가까운 선행 | [Inria의 GNOME 보고](https://radar.inria.fr/rapportsactivite/intranet/PDF-2013/logiciels-.pdf)는 Android 사용자가 이동자료에서 추론 가능한 정보를 확인하고 공개 전 정제를 선택하는 베타 앱을 설명. 보고서 검색 추출문을 확인했으나 PDF 재검색은 404로 실패 |

| 첫 시연 가설 | 명시적 모의 참조 신호에서 제거 전후 후보 결과와 최소 증거 조각을 비교. 실제 주행 공격 성공이나 개인정보 보호 효과로 표현하지 않음. 현재 구현·실행하지 않음 |
| 판정 | 위험 실험→가공→재시험 자체는 선행. 비GPS 차량 신호 적용과 소비자 화면만으로는 통과 부족. 최소 누출 증거 선택이 별도 새 동작과 효용을 만드는지, 실제 자료 수신 목적이 있는지 미입증이므로 최종 추천에서 제외 |

이 판정은 개인정보 영역 전체가 사용자 금지라는 뜻이 아니다. 사용자가 제외한 임시 계정·삭제·개인/공유 화면과 구별해 조사했으며, 이번에는 핵심 처리 차이와 사용 목적 확보가 부족해 통과시키지 않았다. 다른 앱의 직접 데이터 접근을 이 앱이 통제할 수 있다고 가정하지 않는다.

### 주행에 맞춰 읽기 방식을 바꾸는 미디어 가설

차량 운동에 따라 시각자료 표시를 바꾸거나 읽기를 멈추고 듣기로 전환하는 가설을 검토했다. 단순한 멀미 기록과는 다른 개입이지만, [2017년 MotionReader 연구진 공개본](https://www.cs.purdue.edu/cgvlab/www/resources/papers/Hanau-Auto_user_interfacces-2017-Motionreader_Visual_acceleration_cues.pdf)은 차량 가속 시각 단서를 넣은 전자책을 제안한다. [2025년 시험장 연구](https://www.sciencedirect.com/science/article/pii/S1369847825001548)는 운동 예고 단서, 부담이 큰 구간의 읽기 중지, 오디오북을 비교한다. 코디네이터는 원문 제공처의 검색 추출문을 확인했으며 전체 연구 설계·결과는 대조하지 않았다. 관측 값에 맞춰 표시 방향을 바꾸는 구조는 [US20190047498A1](https://patents.google.com/patent/US20190047498A1)에도 공개돼 있다. 이 역시 검색 추출문 확인이며 권리 판단이나 상용화 확인은 아니다.

따라서 가속 단서·읽기 중지·오디오 전환 자체를 새 기능으로 추천하지 않는다. 사용자별 효과·운동 데이터 정확도도 확인하지 않았으며, 앞좌석 중앙 화면의 주행 중 표시 제한을 동승자용이라는 이유로 우회할 수 없다. 별도 신규 처리 차이가 없는 현재 가설은 통과시키지 않는다.

### 초보 운전자의 사후 행동 비교 가설

주행 중 조작 없이 종료 후 자기 행동의 대안을 비교하는 가설을 검토했다. [Volvo Car UK의 2026-08-13 공식 발표](https://news.cision.com/volvo-car-uk/r/new-safety-coach-app-helps-volvo-drivers-build-safer-habits-and-lower-insurance-rates,c4382512)는 제동·가속·코너링 기반 팁과 개인화 점수를 인포테인먼트와 모바일 앱에서 제공하는 Safety Coach 도입을 안내한다. 스웨덴·노르웨이부터 차종·시장별 순차 도입한다고 밝혔으며 모든 시장에 출시 완료한 것으로 해석하지 않는다. 코디네이터가 발표 본문을 직접 확인했다.

점수 대신 '다르게 조작했으면 어땠을까'를 제시하는 방향도 [2025년 IEEE Access 연구의 대학 원문 초록](https://yonsei.elsevierpure.com/en/publications/data-driven-driver-training-via-counterfactual-and-language-based/)에서 이미 SHAP 기반 반사실 행동 변경과 자연어 코칭으로 제안했다. 이는 레이싱 시뮬레이터 연구이며 일반 도로·실차 효과까지 입증한 자료가 아니다. 코디네이터는 연구기관 초록을 직접 확인했지만 논문 전체는 대조하지 않았다.

이 두 자료가 자기 차 주차 궤적의 특정 조작 한 번을 바꾸는 인터랙션까지 동일하게 제공한다고 확인한 것은 아니다. 그러나 사후 코칭·반사실 설명 자체를 신규 핵심으로 삼을 수는 없다. 조향·기어·속도만으로 장애물·주차선·보행자·시선·타이어 미끄러짐을 관측할 수 없으므로 대안 궤적을 '더 안전한 주차'로 판정해서는 안 된다. 바퀴 각도·휠베이스·동기화된 이동량을 확보하지 못하면 궤적의 정확도도 보장하지 못한다. 현재는 차별 기능과 필수 관측이 부족해 최종 후보에 포함하지 않는다.

### PARK-01 재검증: 자기 주차의 조작 하나 바꿔보기

주차를 마친 뒤 실제 저속 기동에서 조향 시작 시점 하나를 바꿔 두 모델 결과를 비교하는 안이다. 운전자가 먼저 끝 자세를 예상하고 비교를 확인한다. 주차 성공·충돌 회피·안전한 재시도 경로는 판단하지 않는다. 앞선 반사실 코칭과 경로 편집 도구에 비해 실제 자기 입력의 단일 개입 변수를 예상→비교하는 동작이 차별 가설이며, 동일한 기능이 공개 선행에 없는 것으로 확정하지 않았다. 점수·게임으로 구성하지 않는다.

- 필수 데이터: ① Pleos 조향각, ② AAOS 속도·기어·원본 시각, ④ 차량 휠베이스와 실험 구간 선택, ⑤ 직접 구축할 저속 운동 모델·오차 범위. 차종 제원을 자동 확보했다고 가정하지 않는다.
- 기술 조사 진전: [실제 읽기 최소 실험](../4000_테스트/4001_SDK_검증_결과.md#에뮬레이터-읽기-호출-최소-실험)에서 Vehicle 2.3.2 조향각 capability/get/반복 callback, AAOS 속도·기어 조회를 에뮬레이터에서 확인했다. static 0값의 반복이므로 주차 입력의 동적 기록 성공은 아니다.
- 핵심 미확인: 반환된 조향 capability 범위는 -470~500이며, 문서의 앞바퀴 각도에 실제 값이 어떻게 대응하는지 확인하지 못했다. 이를 그대로 bicycle model에 넣지 않는다. 비영점 신호·속도 부호·기어 전환·시간 정렬·wheelbase와 실측 경로 오차 확인이 필요하다.
- 추가 공식 근거: [Virtual Console 가이드](https://document.pleos.ai/en/docs/pleos-only/app-test-guide/virtual-console-guide)는 조향 입력을 운전대 각도 -540~540도로 안내한다. SDK의 앞바퀴 각도 설명과 입력·출력 변환 관계를 별도로 확인해야 한다. 용어 차이만으로 오류나 조향비를 확정하지 않으며 실제 가상 입력 대조는 미실행이다.
- 첫 시연: 검증된 저속 신호를 기반으로 자기 기동 재생과 단일 조향 시점 변경을 비교. 실제 신호 의미를 확인하지 못하면 명시적 모의 자료로 UI만 보여주고 기술 실현성 통과로 계산하지 않는다.
- 탈락 조건: 승인된 경로로 필수 신호를 얻지 못함, 입력 오차가 개입 효과보다 큼, 기존 반사실 운전 지도와 사용자 행동 차이가 충분하지 않음, 관찰하지 않은 장애물에 대한 안전 판단이 있어야만 가치가 성립함.

현재는 기술 가설의 일부만 해소한 상태이며 최종 추천·통과 후보가 아니다. 저속 모델 계산 가능성과 실제 사용자에게 유용한 새 학습 경험은 서로 다른 검증 항목이다.

가까운 처리 원리도 추가 대조했다. [EP4114712A1 원문](https://patents.google.com/patent/EP4114712A1/en)은 사용자가 기록한 주차 궤적 중 일부를 대체 궤적으로 바꾸어 자동 추종하는 기술을 설명한다. 따라서 실제 기록 경로의 일부 재계산 자체는 신규 근거가 아니다. [BranchDrive 공개 초록](https://arxiv.org/abs/2609.27275)은 같은 주행 이력에서 조향·가감속 개입을 달리한 CARLA 시뮬레이터 결과들을 비교하는 데이터셋을 제안하며, 정확한 인과 효과나 안전 개선을 입증하지 않는다고 한계를 명시한다. 코디네이터는 특허 원문과 논문 초록을 확인했다. 둘 다 개인 운전자가 자기 주차 조작을 예상→비교하는 교육 앱과 동일하다고 확정할 자료는 아니지만, 반사실 분기·부분 궤적 재계산을 새로운 원리로 주장할 수 없게 하는 반론이다. 사용자 행동 차이를 입증하는 비교가 계속 필요하다.

## 미정 사항과 다음 조사

- 신규 기능 3개는 미확보이며 현재 최종 추천을 작성할 근거가 부족하다. 목표는 재개되어 `active`다. 최종 후보 수를 채우기 위한 약한 추천은 하지 않는다.
- 최신 사용자 조건은 공개 제품·논문·특허에서 핵심 차이를 확인하고 미확인 범위를 명시하는 것이다. 이를 모든 공개·비공개 선행의 절대 부재 증명으로 해석했던 이전 차단 판단은 과도했으며, 독립 검토에서도 이를 확인했다. 절대 부재를 입증하지 못한다는 이유로 조사를 중단하지 않는다. 세계 최초라는 주장은 하지 않는다.
- 통과에는 서로 다른 사용자 과업, 선행의 입력→핵심 동작→결과와의 실질 차이, 차량에서 제공할 추가 가치, 근거 있는 문제와 시작·종료 흐름, 데이터·권한별 구현 경로와 최소 실험, 미확인 범위 공개가 모두 필요하다. 이름·대상·센서·화면만 바꾼 후보는 통과시키지 않는다.
- 서로 다른 사용자 과업은 최종 3개 후보 사이의 독립성 기준이다. 선행과 같은 문제를 해결한다는 사실만으로 자동 탈락시키지 않는다. 같은 문제라도 핵심 처리 방식의 차이가 실제 해결 결과나 가능한 행동을 바꾸는지 확인한다. 앞선 후보의 탈락은 해당 과업의 영구 금지가 아니라 확인된 차이 부족 또는 구현 제약에 대한 현재 판단이다. 사용자가 명시적으로 제외한 영역은 계속 제외한다.
- 완료감사에서 후보 3~5개 표·최종 추천·최종 후보 시나리오·후보별 구현 가능성·신규 기능 3개 모두 전체 충족되지 않았음을 확인했다. LOST-01의 상세 과업·선행 비교·최소 실험 조건은 부분 산출물이며 최종 통과 후보가 아니다.
- 다음 발굴에서는 같은 과업의 화면·표현 변경, 센서 제거, 권한 잠금만 더하는 후보를 먼저 차단한다.
- 통과할 후보가 나오면 사용자 문제·시작/종료 흐름·경쟁 원문·데이터 경로·권한·최소 실험·탈락 조건을 개별 카드로 작성하고 독립 검증에 넘긴다.
- 차량 API 실행이 필요한 최소 실험은 사용자가 지정한 검증 범위와 실제 준비 환경에서 수행하고, 미실행은 그대로 표시한다.
