# 문서 관리

## 핵심 규칙과 참조 안내

- 문서는 SDLC 다섯 단계의 큰 분류를 유지한다. 내부 번호와 하위 분류는 이 프로젝트의 실제 문서 구성에 맞게 정한다.
- 제목의 띄어쓰기는 `_`로 표현한다.
- 다른 프로젝트의 내부 번호·예약 순서를 복사하지 않는다. 문서가 늘어나면 주제에 따라 하위 폴더로 분리한다.
- 사용자 요구와 조건은 누락 없이 보존하고, 미정 사항은 임의로 확정하지 않는다.
- 사용자가 지정한 개발 방법론과 작업 범위를 적용한다.
- 기본적으로 구현을 마친 뒤 사용자가 선택한 검증을 수행한다. 구현 완료와 검증 완료는 구분한다.
- 같은 내용은 원본 한 곳에서 관리하고, 관련 문서에서는 상대 경로와 요구사항 ID로 참조한다.

처음에는 이 문서 전체를 읽고, 이후에는 아래 기준에 따라 필요한 규칙을 참조한다. 이 요약은 상세 규칙을 대체하거나 예외를 만드는 용도가 아니다.

| 작업 | 참조할 항목 |
| --- | --- |
| 폴더·파일 생성 및 이동 | SDLC 기준 분류, 번호 및 이름 규칙, 구성 예시 |
| 문서 작성 및 수정 | Markdown 공통 구성, SDLC 단계별 필수 내용, 내용 누락 방지와 추적 규칙 |
| 개발 방법론 적용 및 구현 진행 | 개발 방법론과 작업 기준, 문서 읽는 순서와 기준 문서 |
| 외부 문서·도구·스킬 사용 | 외부 자료와 도구 적용 |
| 검증 계획 및 실행 | 검증 선택 및 실행 시점 |
| 문서 연결 및 분리 | 문서 참조와 분리 기준 |
| 문서 작업 마무리 | 문서 작성·수정 완료 점검 |

## 기본 원칙

- 문서는 소프트웨어 개발 생명주기(SDLC)를 기준으로 분류한다.
- 문서 내용과 폴더·파일 제목은 한국어로 작성한다. API 등 널리 사용하는 기술 용어는 그대로 사용할 수 있다.
- 폴더와 문서 이름은 `네_자리_번호_타이틀` 형식으로 작성한다. 예: `1000_요구사항_분석`, `1001_서비스_개요.md`.
- 타이틀의 띄어쓰기는 언더바(`_`)로 표현한다.
- 내부 번호는 해당 SDLC 큰 분류의 번호 범위에서 중복 없이 정한다. 특정 문서 종류에 번호를 고정하지 않는다.
- 이 파일(`문서_관리_규칙.md`)은 문서 관리 규칙을 안내하는 파일이므로 번호 규칙의 예외로 둔다.

## SDLC 기준 분류

`docs/` 바로 아래의 기본 폴더는 다음 다섯 단계로 구성한다.

| 폴더 | 관리 내용 |
| --- | --- |
| `1000_요구사항_분석` | 서비스 목적, 개발 범위, 기능 요구사항, 비기능 요구사항, 업무 정책 |
| `2000_설계` | 시스템 구조, 데이터베이스, API, 화면 및 사용자 흐름 |
| `3000_구현` | 개발 환경, 코드 작성 규칙, 구현 지침 및 주요 구현 결정 |
| `4000_테스트` | 테스트 계획, 시나리오, 완료 조건에 따른 검증 및 테스트 결과 |
| `5000_유지보수` | 배포 및 운영 절차, 장애 대응, 운영 중 변경 사항 |

문서는 해당 단계의 폴더에서 관리하며, 개발 이후 요구사항이나 설계가 변경되면 원본 문서도 함께 갱신한다.

## 번호 및 이름 규칙

### 최상위 폴더: `x000_타이틀`

천의 자리 숫자로 SDLC 단계를 구분한다.

- `1000_요구사항_분석`
- `2000_설계`
- `3000_구현`
- `4000_테스트`
- `5000_유지보수`

### 내부 번호와 하위 분류

- 큰 분류 아래의 문서 번호·순서·하위 폴더는 작업자가 실제 주제와 문서 수를 보고 정한다. 내부 번호를 정하기 위해 매번 사용자에게 확인하지 않는다.
- 요구사항은 `1001`~`1999`, 설계는 `2001`~`2999`처럼 해당 SDLC 단계의 범위를 사용한다. 문서와 분류 폴더의 번호는 프로젝트 내에서 중복되지 않게 한다.
- 서비스 개요·개발 범위·요구사항 추적표 등 문서 종류별로 고정 번호를 지정하거나, 다른 프로젝트의 번호를 가져와 빈 번호를 예약하지 않는다.
- 하위 폴더는 관련 문서를 묶을 필요가 있을 때 만든다. 깊이별 자릿수 배분이나 폴더당 9개 파일 제한을 강제하지 않는다.
- 기존 문서 번호는 불필요하게 바꾸지 않는다. 번호를 변경하면 내부 링크·relations·인덱스를 함께 갱신하고 요구사항 ID는 유지한다.
- 아래 구성 예시는 분류를 설명하기 위한 예일 뿐, 이 프로젝트의 내부 번호 배치나 예약 목록이 아니다.

## 작성 및 변경 기준

- 같은 내용을 여러 문서에 복사하지 않고, 원본 문서의 상대 경로를 링크하여 참조한다.
- 요구사항, 설계, 테스트 등 서로 관련된 문서는 링크로 연결한다.
- 문서의 위치는 작성 시점이 아니라 내용이 속하는 SDLC 단계를 기준으로 정한다.
- 기존 번호는 유지하고 새 문서는 사용하지 않은 번호로 추가한다. 정렬을 바꾸기 위해 기존 문서를 일괄 재번호화하지 않는다.
- 문서를 이동하거나 이름을 변경하면 해당 문서를 참조하는 링크도 함께 수정한다.

## 개발 방법론과 작업 기준

- SDLC 폴더는 문서를 분류하는 기준이며, 폭포수 방식으로 순차 개발하라는 의미가 아니다.
- 사용자가 지정한 개발 방법론, 작업 순서, 기술 스택, 산출물 및 검증 방식은 해당 범위의 작업 기준으로 적용한다. 문서의 기본 규칙과 충돌하면 사용자의 명시적 지시를 우선하고 관련 문서를 갱신한다.
- 애자일, 스크럼, 폭포수, TDD 등 방법론을 임의로 지정하지 않는다. 지정되지 않았으면 `미정`으로 기록한다. 해당 결정 없이 진행 가능한 문서 작성과 작업은 계속한다.
- 방법론이 결정되면 설계 단계의 공통 개발 기준 문서에 방법론, 적용 범위, 선택 이유, 작업 단위, 진행 순서, 검토 시점, 완료 기준 및 변경 절차를 기록한다.
- 기능별로 다른 방식이 지정될 수 있다. 각 지정의 적용 범위와 예외를 기록하고 전체 프로젝트에 임의로 확대하지 않는다.
- 방법론이 변경되어도 기존 요구사항과 결정 사항을 삭제하지 않는다. 변경 이유와 영향을 기록하고 설계·구현·테스트·운영 문서를 함께 확인한다.

## 외부 자료와 도구 적용

- 라이브러리·외부 API의 사용법과 설정은 적용할 버전의 문서로 확인한다. 외부 자료를 문서에 반영할 때 출처·버전·실제 확인 범위를 남긴다.
- 도구의 미제공·연결 실패·검색 결과 없음은 해당 사실로 기록하고 공식 문서 등 확인 가능한 근거로 보완한다. 도구 설정이나 호출 시도만으로 조회 성공을 기록하지 않는다.
- 다른 프로젝트의 작업 지침을 참고할 때는 공통 규칙과 프로젝트 전용 설정·경로·명령을 구분한다. 현재 프로젝트에서 존재하지 않는 개발 기준·스킬·도구 설정을 필수 참조로 링크하지 않는다.
- 사용자 지시가 참고 프로젝트의 규칙과 다르면 사용자 지시를 우선한다. 내부 번호·하위 분류·파일 수는 이 프로젝트의 번호 규칙을 유지하고 다른 프로젝트의 고정 번호·제한을 자동으로 가져오지 않는다.
- 스킬이 제안하는 자체 감사·브라우저 검증·문서 생성도 사용자가 지정한 작업·검증 범위 안에서 수행한다. 문서 작성이나 도구 적용이 검증 범위를 자동으로 늘리지 않는다.
- 외부 API를 조사할 때 공식 가이드·소스·배포 바이너리·실행 결과를 구분한다. 선언이나 설정의 존재를 실제 연결·동작 성공으로 표시하지 않는다.

## 검증 선택 및 실행 시점

- 검증 종류, 범위, 실행 시점 및 수행 주체는 사용자가 선택한다. 별도 지정이 없으면 요청된 개발 범위의 구현을 마친 뒤 검증을 진행하는 방식으로 관리한다.
- 개발 중 테스트, 빌드, 린트, 타입 검사 등 검증 명령을 반복 실행하는 것을 기본 절차로 두지 않는다. 사용자가 선택하거나 이미 지시한 검증 범위에서 실행한다.
- 구현 완료 후 검증 방법과 명령, 대상 범위를 정리한다. 선택이 아직 없으면 `검증 선택 대기`로 기록하고 사용자에게 선택을 요청한다. 선택하지 않은 검증을 임의로 추가 실행하지 않는다.
- 사용자가 직접 검증하는 경우 실행 방법과 기대 결과를 제공하고, 결과를 전달받기 전까지 `미검증`으로 유지한다.
- `구현 완료`와 `검증 완료`를 별도 상태로 관리한다. 검증을 미뤘다는 이유로 구현 완료를 표시하지 못하게 하지 않으며, 검증 전에는 기능의 정상 동작이나 테스트 통과를 확정하지 않는다.
- 테스트 계획과 완료 조건은 개발 전에 정리할 수 있지만, 문서 작성이 검증 실행을 의미하지는 않는다. 미실행 결과 항목은 `미실행`으로 표시한다.
- 이후 사용자가 TDD 등 개발 중 검증이 필요한 방법론을 지정하면 그 지시에 맞춰 실행 시점을 조정한다. 지정 범위를 넘어 검증을 확대하지 않는다.
- 아래 문서 점검은 내용 누락과 참조 오류를 확인하는 작성 작업이며, 개발 중 자동 테스트를 실행하라는 의미가 아니다.

## 문서 읽는 순서와 기준 문서

1. 이 문서에서 분류 및 작성 규칙을 확인한다.
2. 서비스 개요, 개발 범위, 개발 진행 기준을 확인한다.
3. 작업 대상의 요구사항과 공통 정책을 읽는다.
4. 관련 설계, 구현 지침, 테스트 및 운영 문서를 읽는다.
5. 문서의 관련 링크를 따라 의존 기능과 미정 사항을 확인한다.

모든 문서를 매번 읽는 대신 작업에 영향을 주는 문서를 빠짐없이 확인한다. 필요한 문서가 없으면 없는 사실을 기록하고, 누락된 내용을 확정된 사실처럼 추정하지 않는다.

| 내용 | 기준 문서 |
| --- | --- |
| 서비스 범위, 기능, 정책, 완료 조건 | 요구사항 분석 문서 |
| 기술 구조, 데이터, 인터페이스, 화면 동작의 구현 방식 | 설계 문서 |
| 환경 구성, 코드 규칙, 구현 절차와 결정 | 구현 문서 |
| 검증 절차, 실행 결과 및 결함 | 테스트 문서 |
| 배포, 운영, 복구 절차 | 유지보수 문서 |

문서 간 충돌은 파일 번호, 수정 날짜 또는 문서 상태만으로 임의 해결하지 않는다. 사용자의 명시적 결정으로 해결할 수 있으면 근거와 함께 반영하고, 해결할 수 없으면 충돌 내용과 영향을 기록하여 사용자에게 확인한다. 충돌과 무관한 작업은 계속한다.

## 구현 시 문서 사용 규칙

- 구현을 시작하기 전에 작업 범위에 해당하는 요구사항, 공통 정책, 설계 및 구현 지침을 읽는다. 파일 이름이나 요약만으로 구현하지 않는다.
- 읽은 문서의 `관련 문서`를 따라 적용되는 조건·예외·권한·의존 기능을 확인한다. 작업 범위와 무관한 문서는 제외할 수 있지만, 필요한 참조를 생략하지 않는다.
- 작업 시작 시 참조 문서의 경로, 관련 요구사항 ID, 반영할 조건 및 미정·충돌 사항을 작업 계획이나 진행 보고에 간단히 정리한다.
- 기존 코드와 문서가 다르면 기존 코드를 곧바로 기준으로 삼지 않는다. 차이와 근거를 확인하고, 사용자 결정으로 해결할 수 없는 충돌은 확인을 요청한다. 영향받지 않는 작업은 계속한다.
- 문서에 없는 기능이나 정책을 임의로 추가하지 않는다. 구현에 필요한 세부 선택은 확정된 요구사항과 설계 범위 안에서 결정하고, 중요한 선택과 근거를 관련 문서에 기록한다.
- 구현 중 새로운 요구나 문서 변경이 생기면 관련 문서를 다시 읽고 영향받는 작업을 조정한다. 이전에 읽은 내용만으로 계속 진행하지 않는다.
- 구현을 마치면 요구사항별 구현 위치와 남은 항목을 추적표에 반영하고, 변경된 설계·구현 문서와 양방향 관련 링크를 함께 갱신한다.
- 완료 보고에는 반영한 요구사항, 주요 구현 위치, 미정·미구현 항목 및 검증 상태를 포함한다. 문서와 구현의 대응 확인은 선택되지 않은 테스트를 실행하는 근거가 아니다.
- 루트 `AGENTS.md`에는 문서 작업뿐 아니라 구현 작업 전에도 `docs/문서_관리_규칙.md`를 읽고 이 사용 규칙을 따르도록 안내한다. 이 문서가 존재한다는 이유만으로 자동으로 읽힌다고 가정하지 않는다.

## OKF 형식과 관계 관리

- `docs/`를 OKF v0.2 지식 번들의 루트로 사용한다. SDLC 폴더·네 자리 번호·파일당 본문과 요구사항 ID를 유지한다. 루트 `AGENTS.md`와 `README.md`는 번들 밖에 두고 변환하지 않는다.
- 모든 개념 문서는 YAML frontmatter로 시작한다. 공식 필수 필드는 `type`이며 프로젝트에서는 `title`, `description`, `status`, `tags`, `relations`도 작성한다. `type`은 Requirements, UserFlow, Policy, Scope, Design, Architecture, Guide 등을 사용한다.
- `status`는 `draft`, `stable`, `deprecated`를 사용한다. 초안·검토 중은 `draft`, 사용자 또는 합의된 절차로 확정한 문서는 `stable`, 폐기 문서는 `deprecated`다. 본문 상태와 일치시키고 변환만으로 확정하지 않는다.
- `relations`는 프로젝트 확장 필드이며 공식 OKF 필수 필드나 정식 온톨로지 표준이 아니다. 각 항목은 `type`과 해당 문서 기준 상대 경로 `target`을 가진다. 관련 문서가 없으면 `[]`로 둔다.
- 관계 어휘: `refines`(대상을 구체화), `refined_by`(대상이 현재 문서를 구체화), `depends_on`(대상 정책·설계에 의존), `required_by`(대상이 현재 문서에 의존), `related_to`(일반 연관). 구현·검증 관계가 필요하면 `implements`/`implemented_by`, `verifies`/`verified_by` 쌍을 사용한다. 설계 문서가 아직 초안이면 실제 구현 완료 관계로 표시하지 않는다.
- 관계 추가·수정 시 대상 문서의 역관계와 본문 `관련 문서` 링크를 함께 갱신한다. `related_to`는 양쪽에 같은 유형으로 적는다. 각 방향의 target은 해당 파일 기준으로 계산한다.
- 구조화된 관계는 탐색용이며 본문의 참조 목적·조건·예외를 대체하지 않는다. 동일 대상을 다른 표현으로 중복 등록하지 않고 누락·불일치를 수정한다.
- 문서 관리 규칙과 AGENTS는 작업 지침이므로 제품 문서의 relations 및 관련 문서 연결 대상에서 제외한다. 인덱스에는 문서 관리 규칙의 진입 링크를 둘 수 있다.
- 각 문서 폴더의 `index.md`에는 직속 문서의 링크·한 줄 설명과 하위 폴더 인덱스 링크를 둔다. 인덱스는 개념 문서가 아니며 frontmatter를 넣지 않는다. 번들 루트 인덱스에는 `okf_version`만 표시할 수 있다.
- `index.md`는 탐색용 예약 파일로 번호 규칙의 예외다. 문서 수가 늘어나면 읽기 편의에 따라 하위 분류와 인덱스를 정리한다.
- 출처·생성·검증 정보를 실제로 확인한 경우 공식 `sources`, `generated`, `verified` 필드로 추가할 수 있다. 확인하지 않은 검증·작성자·시각은 만들지 않는다. 현재 본문의 근거를 삭제하지 않는다.
- 이력은 Git으로 관리하고 선택 파일인 `log.md`는 만들지 않는다. 미래·미작성 문서는 관계를 만들지 않고 본문의 미정 사항에 남긴다.
- 공식 기준: [Open Knowledge Format v0.2](https://github.com/GoogleCloudPlatform/open-knowledge-format/blob/main/SPEC.md). 프로젝트 규칙이 공식 최소 규칙보다 엄격한 부분은 프로젝트 내부 규칙으로 구분한다.

## Markdown 공통 구성

문서 하나는 하나의 주제를 다룬다. 제목은 하나의 `#`로 작성하고, 아래 공통 항목을 `##`로 구분한다. 실제 내용을 쓰는 본문에는 단계별 필수 항목을 추가한다.

```markdown
---
type: Requirements
title: 문서 제목
description: 문서의 한 줄 설명
status: draft
tags: [요구사항]
relations: []
---
```

## 내용 누락 방지와 추적 규칙

- 사용자가 제공한 요구, 조건, 예외, 수치, 용어, 제약 및 방법론을 모두 문서화한다. 요약 과정에서 의미나 조건을 삭제하지 않는다.
- 원본 자료를 항목별로 나누어 요구사항 또는 결정 ID를 부여하고 문서 위치와 연결한다. 원문을 보존할 필요가 있으면 관련 SDLC 폴더에 별도 문서로 보관하고 링크한다.
- 요구사항 ID는 `REQ-AUTH-001`, 결정 ID는 `DEC-001`, 테스트 ID는 `TEST-AUTH-001`처럼 관리한다. ID는 파일 번호와 독립적이며 파일 이동이나 이름 변경에도 유지한다.
- 다음 추적표는 `1000_요구사항_분석/`의 요구사항 추적표 문서에서 관리한다. 파일 번호는 현재 문서 구성에 맞게 정하고 고정하지 않는다. 각 항목은 추후 연결할 위치까지 추적하며, 아직 없는 연결은 `미작성`, `미구현`, `미검증` 등 실제 상태로 표시한다.

| 요구사항 ID | 요구 및 근거 | 요구사항 문서 | 설계 문서 | 구현 위치 | 테스트 및 결과 | 상태 |
| --- | --- | --- | --- | --- | --- | --- |

- 요구사항뿐 아니라 공통 정책과 비기능 요구사항도 추적한다. 사용자의 보류·취소 결정은 이유와 함께 남기고 항목을 삭제하여 숨기지 않는다.
- 변경 시 원본 항목과 수정 문서를 대조하여 조건·예외·수치가 모두 보존되었는지 확인한다. 관련 설계·구현·테스트·운영 문서의 영향도 함께 확인한다.
- 요구사항 변경을 설계나 구현 문서에만 반영하지 않는다. 요구사항 원본과 추적표를 먼저 또는 함께 갱신한다.
- `구현 완료`는 요청된 범위의 코드 작성이 끝났을 때 표시하고, 검증 상태를 함께 기록한다. `검증 완료`는 사용자가 선택한 검증의 실제 결과와 해당 완료 조건을 연결했을 때 표시한다. 미정 사항, 미구현 항목, 미실행 테스트 및 선택하지 않은 검증 범위는 그 사실과 영향을 명시한다.

## 문서 참조와 분리 기준

- 참조할 때는 링크만 나열하지 않고 해당 문서를 읽어야 하는 이유와 적용 범위를 함께 적는다.
- `관련 문서`에는 내용상 연관된 기획·설계·구현·테스트·운영 문서만 연결한다. `문서_관리_규칙.md`와 `AGENTS.md`는 작업 지침이므로 연결 및 양방향 링크 갱신 대상에서 제외한다. 관리 규칙 문서에도 개별 프로젝트 문서 목록을 두지 않는다.
- 문서 생성·수정으로 관련 문서가 새로 생기거나 관계가 변경되면, 현재 문서뿐 아니라 연관된 기존 문서의 `관련 문서` 링크도 함께 갱신한다. 양쪽 문서에서 서로 찾아갈 수 있도록 참조 목적, 적용 범위 및 관련 요구사항 ID를 반영한다.
- `관련 문서`에는 문서 역할, 상대 경로, 관련 요구사항 ID를 기록한다. 필요한 경우 해당 제목으로 이동하는 앵커도 사용한다.
- 요구사항의 원본, 설계 방식, 테스트 기준을 구분하여 연결한다. 참조 문서의 내용을 복사해 별도의 원본으로 만들지 않는다.
- 참조 대상에서 작업에 영향을 주는 공통 정책, 조건, 예외 및 의존 문서까지 확인한다. 일부 문단만 읽고 나머지 조건을 누락하지 않는다.
- 외부 자료는 출처 링크와 실제로 확인한 버전 또는 날짜, 적용 부분을 기록한다. 확인하지 못한 자료는 `미확인`으로 표시한다.
- 아직 존재하지 않는 내부 문서는 링크 대신 작성 예정 경로와 상태를 표시한다. 문서를 생성한 뒤 실제 링크로 변경한다.
- 문서 이동·분리 시 기존 참조를 수정하고, 이동한 내용과 새 위치는 커밋 메시지에 기록한다.
- 문서의 변경 이력은 Git 커밋으로 관리한다. 문서마다 변경 이력 표나 커밋 해시를 중복 기록하지 않는다. 현재 정책의 결정 근거·조건·미정 사항은 본문에 유지하며, 변경 이유·내용·검증 상태는 커밋 메시지 생성 규칙에 따라 기록한다. 커밋은 사용자가 직접 수행한다.
- 문서 길이에는 강제 제한을 두지 않는다. 약 300줄을 넘으면 분리를 검토하되, 줄 수보다 주제의 독립성과 읽기 편의성을 기준으로 판단한다.
- 분리 시 조건·예외·수치·근거를 빠짐없이 옮기고 상위 문서에 하위 문서의 역할과 링크를 남긴다. 길이를 줄이기 위해 요구사항을 삭제하거나 의미를 축약하지 않는다.
- 이 문서는 문서 관리 규칙만 유지한다. 개별 기능 요구사항, 실제 기술 설계, 개발 방법론의 프로젝트별 결정 및 테스트 결과는 해당 SDLC 문서에서 관리한다.

관련 문서 표의 작성 형식은 다음과 같다.

| 문서 역할 | 문서 | 참조 목적 및 적용 범위 | 관련 요구사항 ID |
| --- | --- | --- | --- |
| 요구사항 원본 / 설계 / 테스트 / 공통 정책 등 | 실제 상대 경로 링크 | 읽어야 할 내용과 작업에 적용할 범위 | 관련 ID 또는 해당 없음 |

## 문서 작성·수정 완료 점검

- [ ] 사용자 지시와 원본 자료의 모든 항목이 문서 또는 추적표에 연결되어 있다.
- [ ] 기존 내용의 조건·예외·수치가 누락되거나 임의로 변경되지 않았다.
- [ ] 사용자가 지정한 방법론과 적용 범위가 반영되어 있다.
- [ ] 공통 구성과 단계별 필수 항목을 작성하거나 미정·해당 없음의 이유를 표시했다.
- [ ] 문서 상태, 근거, 관련 요구사항 및 미정 사항이 명확하다.
- [ ] SDLC 큰 분류의 번호 범위를 따르고 번호 중복이 없다.
- [ ] 내부 번호와 하위 분류는 현재 프로젝트에 맞게 정했으며 다른 프로젝트의 고정 번호·예약 순서를 적용하지 않았다.
- [ ] 관련 링크의 경로와 대상이 실제로 존재한다. 아직 없는 문서는 링크 대신 작성 예정 경로와 상태를 표시했다.
- [ ] 이동·분리·변경에 따른 참조와 추적표를 갱신했다.
- [ ] 생성·수정한 문서와 연관된 기존 문서의 관련 링크를 함께 갱신하여 양쪽에서 참조할 수 있다.
- [ ] 실행하지 않은 검증을 통과로 기록하지 않았다.
- [ ] OKF frontmatter와 본문 상태가 일치하고 relations·역관계·관련 링크·폴더 인덱스를 함께 갱신했다.
